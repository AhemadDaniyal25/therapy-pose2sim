Last checked 2026-10-20. If you read one file in this repo, read this one.
every result in the project is downstream of it.

## Board

DICT_4X4_50, 7×5 squares, 50 mm square / 37 mm marker → 24 interior corners.

## Intrinsics: verified

Re-estimated from the ChArUco clips with an **80/20 held-out split**.
calibrate on 80% of detected frames, report error on the 20% the optimiser
never saw. Training-only RMS always looks good and proves nothing.

| camera | held-out RMS |
|---|---|
| main | 0.350 px |
| left | 0.594 px |
| right | 0.869 px |

Sub-pixel on unseen frames. Intrinsics are sound. Also sane on inspection:
fx in a plausible range for the sensor width, principal points *near but not
exactly at* the image centre (which is what a real estimate looks like),
small distortion coefficients.

Contrast with the broken TOML: fx = 8712 px on a 1080-px image, k1 = −31.8,
every principal point at exactly (959.5, 539.5). Those are the fingerprints
of a calibration that was never actually run.

## Extrinsics: the weak link

Two separate problems.

**1. They were imported, not computed.**
`ali_repo/scripts/import_reference_calibration.py` reads them from an
external codebase at `D:\Master's Data\Project Pose Estimation\Pose
estimation code`. So they were never derived from this footage and cannot be
audited from what we have.

**2. The error metric is in metres and the key name lies about it.**
The npz field is called `rms`, which everyone reads as pixels. The script
that writes it says otherwise:

```python
residual = float(d["mean_translation_residual"])
np.savez(..., rms=np.float64(residual))
print(f"  (pairs={num_pairs}, residual={residual:.4f} m)")
```

So:

| pair | residual | baseline | relative error |
|---|---|---|---|
| main to left | 0.6364 **m** | 2.413 m | **26.4%** |
| main to right | 0.5718 **m** | 3.066 m | **18.6%** |

(Baselines read straight out of the npz by `hpc/verify_hpc.py`. An earlier
version of this file had them the wrong way round, which made main-left
look like the better-calibrated pair. It is the worse one, and that is
consistent with everything else below.)

Not sub-pixel). I reported these as pixels at first and it was wrong (do not
repeat it), and correct it anywhere it still says "0.57 px" (including the
`therapy-room-pose-pipeline` README).

A 20–25% translation error explains everything downstream: biocular widths
of 7.5 and 8.5 cm against an adult range of 8.8–9.8 cm, and bones sitting
1–2 cm below their anatomical floor. The reconstruction is geometrically
consistent and slightly too small.

## Why we can't just redo the extrinsics

Stereo extrinsics need the board visible in **two cameras at the same
instant**. `validation/covisibility.py` scanned 28:00–37:30 at 3 fps:

| pair | co-visible frames at ≥12 corners |
|---|---|
| main + left | **0** |
| main + right | **6** |
| left + right | **0** |

The board was shown to one camera at a time. Correct for intrinsics, useless
for extrinsics. Six frames is not a calibration, and no amount of
re-processing changes that. It's missing data, not a software problem.

(The clips *do* contain the board, which is why "there are calibration
recordings with the ChArUco visible" is true and still doesn't help. The
question isn't whether the board is visible, it's whether it's visible to two
cameras at once.)

The board was also printed too small, A3 at room distance, which is why
`covisibility.py` retries detection at 2× upscale and why the main camera
struggles most.

## Independent evidence that main↔left specifically is the bad one

Person A (left side) is worse than Person B (right side) on every measure
that doesn't share an optimiser:

| | Person A (main↔left) | Person B (main↔right) |
|---|---|---|
| body reprojection | 16.2 px | 3.5 px |
| bone-length robust CV | 0.092 | 0.011 |
| bones in anatomical range | 6/10 | 8/10 |
| face reprojection median | 12.35 px | 1.46 px |
| biocular width | 7.52 cm | 8.53 cm |

Body fitting and face fusion are independent methods with independent
failure modes. Both put Person A at roughly 4–8× worse. That points at the
shared input, the main↔left extrinsic, not at either method.

## For the next recording

Non-negotiable, before any therapy footage:

1. **Record a calibration clip with the board visible to two cameras
   simultaneously**, ~2 min per overlapping pair. Walk it through the
   overlap region slowly, at varied angles and distances. This is the single
   fix that unblocks metric accuracy.
2. **Print the board bigger.** A2 or larger, on rigid board so it stays flat.
3). Then a per-camera pass for intrinsics (board filling the frame, varied
   poses) (the existing protocol, which already works.
4. Keep intrinsics and extrinsics clips as separate labelled files.

New recording = new camera positions = **the existing calibration is
invalid**. It cannot be reused even if nothing looks like it moved. See
`RUNBOOK.md`.

## If the 5-camera setup goes ahead

Planned: 1 × Panasonic AW-UE4WG + 4 × ELP USB 4K, on the supervisor's gaming
laptop via OBS, target 5 × 4K30.

- **Check the USB host controller count first.** Four 4K USB cameras will
  saturate a single USB 3.x controller long before they saturate the CPU.
  `lsusb -t` (Linux) or Device Manager → view by connection (Windows) shows
  how many independent controllers exist. Plan to drop to 1080p30 if they
  share one.
- More cameras means more overlapping pairs to calibrate. Budget real time
  for the board-in-two-views clips (10 pairs if all five overlap).
- A hardware or software sync marker (a clap, a flash, a visible timecode)
  at the start of every take would remove the entire synchronisation problem
  rather than measuring it afterwards.
